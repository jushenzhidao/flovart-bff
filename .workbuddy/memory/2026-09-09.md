## 🔴 /api/shares 报「服务器内部错误」(500) 根因 + 修复（重要）
- 现象：批量共享上线后，点分享提交返回 `{"success":false,"message":"服务器内部错误"}`（来自 `main.py` 全局 `Exception` handler）。
- **根因（两层，均已修）**：
  1. **关键**：本机 BFF 实际走 **SQLite 回退后端**（`USE_PG=False`——`.env` 里**无 `POSTGRES_DSN`**，长期记忆里「PG 是生产存储」的假设在本机不成立！）。而 `LocalMeta` 类**从未实现任何共享方法**（`share_put_batch`/`share_list_*`/`share_get`/`share_delete`/`media_index_get_by_key`/`media_get_shared` 全是抽象 `NotImplementedError`），所以每次共享都抛 `NotImplementedError` → 500。PG 版之前因为管理员登录先挂、从未真正跑到写库行，bug 一直潜伏。
  2. 即便走 PG，`PgMeta.share_put_batch` 的 INSERT **漏了主键 `id` 列**（`cloud_media_shares.id` 是 `PRIMARY KEY NOT NULL` 无默认值）→ 写库也会 500。
- **修复 `app/cloudstore.py`**：
  - `LocalMeta` 补齐全部共享方法 + `cloud_media_shares` 建表（UUID `id`、唯一约束 `(owner_uid,target_uid,media_key)`、owner/target 索引），`media_index_get_by_key` 与 `media_get_shared` 也补齐（与 PgMeta 对称）。
  - `PgMeta.share_put_batch` INSERT 补 `id=uuid.uuid4().hex`。
- **验证（端到端，决定性）**：
  - `USE_PG=False` 直连 `LocalMeta.share_put_batch`：写库返回带真实 `id` 的行 ✅
  - HTTP 冒烟（登录 newapi-bff 拿 `bff_session` cookie）：自共享→400「不能共享给自己」、不存在目标→404「解析用户 X 失败」、空 key→400，均 **非 500** ✅
  - **完整成功共享**：上传图→`GET /api/console/users` 找真实用户 `80e3dac7612447d7ae`(uid 102)→`POST /api/shares` 返回 `200 {shared:1,target_count:1}`→`GET /api/shares`(我分享的) 能查到该行 ✅
  - BFF 已重启（PID 3177→Yov88T，端口 8300，/readyz=200）。测试产生的共享行+媒体已清理。
- ⚠️ **长期约定需修正**：本机 flovart-bff 是 **SQLite 兜底 + 本地文件字节**（`USE_PG=False`/`OSS_ENABLED=False`），非 PG/OSS。任何「共享/媒体/文档」相关改动都要**同时保证 LocalMeta 与 PgMeta 两套后端都实现**，否则切到兜底后端就 500。已把此事实补进 `MEMORY.md`。

## 共享素材图片不渲染 / 下载提示无文件
- 现象：共享卡片能显示，但图片没出来；点击下载提示没有文件；BFF 日志出现 `GET /api/shared/media/undefined` 404。
- 根因（两个独立 bug，均已修）：
  1. **前端字段名映射缺失**：`services/hostedClient.ts` 的 `listSharedMedia`/`listMyShares` 直接把后端 snake_case 数据返回给前端，而 `SharedMediaItem`/`ShareItem` 是 camelCase（`mediaKey`/`ownerUid` 等），结果 `item.mediaKey` 是 `undefined`，请求都打到 `/api/shared/media/undefined`。
  2. **BFF 本地文件响应缺失 import**：`app/routers/shares.py` 用 `FileResponse` 返回本地文件字节，但顶部只 import 了 `RedirectResponse`，导致真正请求有 key 的字节时 `NameError: FileResponse` → 500。
- 修复：
  - 后端 `app/routers/shares.py`：`from fastapi.responses import FileResponse, RedirectResponse`。
  - 后端 `app/cloudstore.py`：`share_list_by_owner`（PgMeta + LocalMeta）JOIN `cloud_media` 取 `kind/mime/size`，让 `/api/shares` 返回正确 `mimeType`。
  - 前端 `services/hostedClient.ts`：`listSharedMedia`/`listMyShares` 做 snake_case → camelCase 归一化，缺失字段给默认值。
- 验证：管理员 cookie 请求 `GET /api/shared/media/{key}` 返回 `200` + `Content-Type: image/jpeg` + 114664 字节；`GET /api/shares` 返回 `mimeType: image/jpeg`；`npx tsc --noEmit` 无新增错误；BFF 已重启（fsObvv→IEV1FK，端口 8300，`/readyz=200`）。

## ⚠️ 切回管理员登录后工作流被清空（隔离改 key 的回归，已修）
- 现象：上轮加了「按 uid 隔离 workflow 存储」后，管理员切回自己账号，发现**自动创建了一个空工作流**，且**原本工作流里的素材图片全没了**。
- 根因：**隔离是两层，缺一层迁移**。
  - 第一层（早已存在、`ns()`）：localforage **数据库名**按 uid 物理隔离（`flovart_workflow_v2__u{uid}`，登录时 `setHostedStorageUid` + reload 重建）。adam 看不到管理员数据主要是这层在起作用。
  - 第二层（上轮我加的）：库内 **persist key** 由 `flovart:workflow:projects` 改成 `flovart:workflow:projects:{uid}`。但**管理员旧数据躺在无后缀旧键下**，切到带后缀新键后读到空 → 自动建空工作流、原始项目（含内嵌素材图片）全读不到。旧键数据本身完好（从未被写），只是没搬过来。
- 修复（`components/workflow/store.ts` + `App.tsx`）：
  - 新增 `migrateLegacyWorkflowStore(uid)`：**一次性**迁移（localStorage 标记 `flovart:workflow:legacy_migrated`）。从旧键 `flovart:workflow:projects` 读数据，按 id 合并到当前账号 `getWorkflowStoreKey(uid)`：保留旧数据全部项目，丢弃「不在旧数据里且为空（无节点/连线/默认标题）」的自动生成空工作流，避免覆盖真实数据又避免残留垃圾。旧键保留作备份、不删。
  - `App.tsx` 的隔离 effect：切 uid 时先 `await migrateLegacyWorkflowStore(uid)` 再 `rehydrate()`。
  - 关键：迁移在「同一个已按 ns 隔离的库」内做，不会跨号串数据；adam 的库里旧键为空，不会误拿管理员数据。
- 验证：`npx tsc --noEmit` 本次改动文件零新增错误（残留为历史遗留）。纯前端改动，无需重启 BFF；飞哥需**硬刷新**浏览器触发迁移（flag 保证一次性）。
