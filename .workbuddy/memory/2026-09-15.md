## 修复：未登记产品模型选中后提交弹「配置 AI 服务」弹框（承接 09-14 晚）

### 现象（飞哥 09-14 21:20 反馈）
设置页已配好 AI 服务（`gpt-image-2.5-flare`，网关 `api.chatfire.cn/v1`），
PromptBar「选择模型」里也能正常列出并选中，但**一提交任务就弹出配置服务弹框**。

### 根因（完整链路已实测复现）
1. `gpt-image-2.5-flare` **未登记进产品目录**，`resolveDisplayableProductModel()` 走合成兜底
   → id = `flovart:custom:gpt-image-2.5-flare`（模型能列出/选中，这步正常）
2. 但 `suggestProductRouteMappings()` **只遍历 `PRODUCT_MODEL_CATALOG`（登记目录），不含合成模型**
   → 推不出任何 routeMapping（实测返回 `[]`）
3. `mergeSuggestedProductRouteMappings()` 也补不出映射 → `routeMappings` 为空
4. `resolveRouteMapping()` 无候选 → 返回 `null`
5. → `activeRoute = null` → PromptBar 判 `missingKey` → `onOpenSettings()` **弹框**

对比：`gpt-image-2` 是**登记模型**，同样流程出 2 条映射，所以从不弹框 —— 这解释了
「2 能用、2.5-flare 不能用」的差异，**与模型本身无关，纯粹是目录登记与否**。

### 修复
`services/productModelCatalog.ts` 的 `suggestProductRouteMappings()`：
在登记目录遍历之后，**为「能推断出创作能力、且未被登记模型消费」的候选模型补一份合成映射**。
- 合成 id 口径与 `synthesizeProductModel` 一致：`flovart:custom:` + `normalize(name)`
- `routeId` 直接用**原始模型名**（发请求时用的就是它）
- ⚠️ 用 `matchedCandidates`（登记结果的 routeId 集合）排除已消费的候选名，
  否则已登记模型会被重复生成一份 custom 映射

### 验证
- 新增回归测试 `tests/unregisteredModelRouting.test.ts`（3 例）：
  ① 未登记模型能推导出映射且 routeId = 原始名
  ② 【端到端】选中后 `resolveProductModelRoute` 非 null（不再弹框）
  ③ 【反向保护】已登记模型 `gpt-image-2` 映射保持 2 条、不含 custom
- **对照组**：把 `return [...registered, ...synthesized]` 临时还原成 `return registered`
  → 前 2 例必失败、第 3 例仍过 → 证明测试锁住了行为
- `tsc --noEmit` = **16 错**（= 基线，无新增）
- 相关套件 30 passed

### ⚠️ 过程中踩的坑
TS 的 `RouteMappingTarget` 是**判别联合**（`kind` 必须是字面量）。用 `.flatMap(mode => ({ target: { kind: 'product-mode', ... } }))`
时 TS 会把 `kind` **宽化成 `string`** → `TS2322`。修法：给变量显式标注 `RouteMappingBinding[]`，
或在字面量上加 `as const`。**这个坑在写 map/flatMap 构造判别联合时很常见。**

## 🔴 修复：新配置的 AI 服务强刷新后丢失（飞哥 09-15 15:52 反馈）

### 现象
设置页新增一个 AI 服务（真 key + `gpt-image-2.5-flare` + `https://api.chatfire.cn/v1`），
点「验证并保存」→ **校验通过、弹窗关闭、无任何报错**；但**强刷新后条目消失**。

### 排查过程（逐层排除，最终定位在加密层）
1. **keyVault 层**（直接调模块写库 → 强刷新读库）：✅ 正常（`_repro_persist.mjs`）
2. **命名空间**：✅ 正确（`flovart__u150`，localStorage/cookie uid 一致）
3. **真实 UI 端到端**：❌ 复现。填表 → 校验 200 → 点保存 → 弹窗关闭 → **vault 里没有新条目**
4. **hook `saveKeysEncrypted`**：❌ 失败 — ES module export 不可重定义（`Cannot redefine property`）
5. **hook IndexedDB 写操作**（`IDBObjectStore.prototype.put/delete/clear` + `page.addInitScript`）：
   ✅ **关键** — 保存后只有 `provider_model_cache` 写，**没有 `provider_secret_vault` 写** → 写库根本没发生
6. **捕获 `pageerror`**：✅ **命中根因**

### 根因（已拿到精确栈）
```
RangeError: Maximum call stack size exceeded
    at encryptKeys   (utils/keyVault.ts:46:22)   ← 当时的 btoa 行
    at async saveKeysEncrypted (utils/keyVault.ts:62:21)
```

`encryptKeys` 末行：
```ts
return btoa(String.fromCharCode(...packed));   // ❌
```
`String.fromCharCode(...packed)` 把**整个密文字节数组展开成函数实参**。
实参数量超过 JS 引擎栈/实参上限（V8 实测 **~128KB 即抛**，node 验证：70KB OK / 130KB RangeError）就抛栈溢出。

**为什么「平台模型」能存、新服务存不进**：表单保存时会把该端点的**全部模型清单**写进
`customModels`/`models` —— 这个网关有 **743 个模型**，序列化后远超阈值。
（平台 Key 池条目模型少，所以一直正常 → 掩盖了这个 bug。）

**为什么用户看不出错**：`saveKeysEncrypted` 把 `encryptKeys` 放在 try **外面**且 fire-and-forget，
异常只打一条 `console.error`；UI 侧 `handleSaveKey` 早已提示「已保存」并关闭弹窗。

### 修复（flovart-web）
1. `utils/keyVault.ts`：新增 `bytesToBase64()`，**分块 32KB**（`String.fromCharCode.apply(null, subarray)`），
   替换两处展开写法；`encryptKeys` 改用它
2. `utils/keyVault.ts`：`saveKeysEncrypted` 返回 `Promise<boolean>`，
   并把 **`encryptKeys` 一并纳入 try**（原来在 try 外，抛错直接变 unhandled rejection 且无上下文）
3. `hooks/useApiKeys.ts`：持久化 effect 检查返回值，失败时打显式告警（不再静默）

### 验证
- 端到端复跑：保存后 vault = `["UI真Key服务","平台模型"]`，**强刷新后仍在** ✅；`PAGEERROR` 消失
- 新增回归测试 `tests/browserPersistence.test.ts` 2 例（大 payload 200KB+ 能存 / 序列化失败返回 false）
- **对照组**：把 `bytesToBase64` 临时还原成 `...packed` → 复现 `RangeError` 且大 payload 用例必失败 → 证明测试锁住了行为
- `tsc --noEmit` = **16 错**（= 基线，无新增）

### ⚠️ 教训
- **不要在 `String.fromCharCode`/`Function.apply` 上传大数组**：一律分块（≥32KB 就要分）
- **fire-and-forget 的持久化 + catch 里只 console.error = 静默数据丢失**：失败必须回传调用方
- 排查「保存后刷新就没了」：hook `IDBObjectStore.prototype` 看**写操作有没有发生**是最快的分界线
  —— 分清了「没写」和「写了但读不回」，直接把范围砍半

## 🚨 git 仓库损坏事故与无损恢复（15:00-15:20）

### 现象
飞哥要求「模拟人使用，在浏览器里点击看看」，收尾时我按惯例想 `git status` 列未提交文件，
结果 **`fatal: not a git repository`** —— 而 `.git/` 目录明明存在、`ls` 也能列出内容。

### 根因链（完整诊断）
1. **`.git/refs/` 目录整个消失**。git 判定仓库需同时具备 `HEAD` + `objects/` + `refs/`，
   缺 refs 就直接不认仓库 → 所有 git 命令失效。
2. **铁证**：`.git/objects/maintenance.lock`（0 字节）+ `bitmap-ref-tips_pIlERI` 残留
   → **`git gc` 跑到一半被中断**（极可能是沙盒/会话终止），清理完 refs 后没来得及重建。
3. `.git/logs/refs/heads/{dev,main,ls}` 的 **reflog 全部幸存**（reflog 与 refs 是两个独立目录），
   从中读回所有分支的 tip SHA —— 这是恢复的关键线索。
4. `packed-refs` 不存在 → ref 信息**没有任何备份**，只能靠 reflog。
5. **更严重**：`objects/pack/` 里有两个 `.idx` 索引文件但**对应的 `.pack` 数据文件已被删**，
   → commit 对象 `f87f30a` / `4cc3001` 物理丢失，`git cat-file -t` 报 `could not get object info`。

### 恢复步骤（无损，全部成功）
```bash
# 1. 重建 refs 三件套（这一步就让 git 重新认出仓库！）
mkdir -p .git/refs/heads .git/refs/tags .git/refs/remotes/origin

# 2. 从 reflog 读回 SHA，重建本地分支 ref
printf '<sha>\n' > .git/refs/heads/dev     # f87f30a ← reflog
printf '<sha>\n' > .git/refs/heads/main    # 4cc3001 ← ls-remote 真实值

# 3. 清 gc 残留锁（否则后续 fetch 会一直等锁）
rm -f .git/objects/maintenance.lock .git/objects/bitmap-ref-tips_*

# 4. fetch 拉回丢失对象 → 实际下载了全新 74MB pack，历史完整回归
git fetch --all --tags

# 5. 删无 .pack 的孤儿 .idx（否则 fsck 刷屏 "failed to load pack entry"）
for idx in .git/objects/pack/*.idx; do [ -f "${idx%.idx}.pack" ] || rm -f "$idx"; done
rm -f .git/objects/pack/multi-pack-index

# 6. 补齐 remote refs（prune 删过，且 fetch 因 SHA 未变不会重建）
printf 'ref: refs/remotes/origin/main\n' > .git/refs/remotes/origin/HEAD
printf '<sha>\n' > .git/refs/remotes/origin/{dev,main}
```

### 结果
- `git fsck` **零输出 exit=0** —— 仓库完全健康
- `git branch -vv` → `main [origin/main]` / `dev [origin/dev]` 追踪正常
- **工作区 20 个已修改 + 1 个未跟踪文件，一个字节没丢**（源文件全部核对字节数）
- 核心修复在位：`productModelCatalog.ts:241` 幂等分流 + 无 REVERT-MARK 残留
- 单测 23 passed、tsc 保持 16 错基线

### ⚠️ 重要认知修正
- **`git status` 的 `A`(added) 数量会骗人**：恢复过程中一度显示 1008 条变更（987 个 `A`），
  那是「HEAD 无法解析时索引相对空树的假象」。HEAD 修好后立刻回落到真实的 22 条。
  **别被 A 的数量吓到，先确认磁盘文件在不在。**
- **`git remote prune origin` 会删掉 `.git/refs/remotes/` 下的物理文件**，
  之后即使 `git ls-remote` 能看到分支，本地也不会自动重建 remote ref 文件。需手工补。
- **判断仓库健康的最快命令**：`.git/refs` 在不在 → 在就 `git fsck`。
- 远端完好是本次能无损恢复的**唯一前提**：`origin/dev=f87f30a`、`origin/main=4cc3001`。
  **本地 commit 后及时 push 的价值在这次事故里体现得很直接。**

## 🔴🔴 续查：普通用户生图仍失败 —— 三个叠加根因（飞哥「还是失败的啊」）

飞哥追问「**为什么管理员可以使用，而普通用户用不了**」——这句问对了方向：

### 根因① 前端连的不是我改的那个 BFF（测试打偏）

- sync 分支**只调 `_run_sync`**，而它内部只有 `request_log_update`（**UPDATE**）；

- 症状：`POST /api/tasks` 返回 `succeeded` + 真实 b64 数据，

- ✅ **顺带**：同时把 sync 改为**非阻塞**（`_spawn_sync_call` + `asyncio.create_task`，
