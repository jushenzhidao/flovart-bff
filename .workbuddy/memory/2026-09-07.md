不认 PAT（PAT 仅用于管理类 `/api/*`）。旧 chat.py 用 `na.user_headers(session["pat"], uid)`

  `admin_mint_user_api_key(uid)`（管理员代建兜底，适配 data.key / data.id 两种返回）。

- 重写 `chat.py`：聊天时 `resolve_user_key` 优先复用已存 sk-，否则按需 mint（先用户 PAT、失败回退

### 后续：服务「挂了」真因 = /readyz 卡 5.7s（已修）+ data/ 写慢环境坑
- **现象**：飞哥报「服务挂了」。实测进程没死：`/api/config` `/healthz` 均 6ms 200，仅 `/readyz`
  稳定 **5.6s** 才返回（探针 5s 超时 → 误判 down）。`/api/*` 业务接口一直正常。
- **根因**：`app/main.py` 的 `_check_state_dir()` 在 `/readyz` 里**每次做真实写探针**
  （`open(probe,"w")` + `os.remove`）。本机 `D:\code\flovart-bff\data\` 下被 Windows Defender/OneDrive
  等文件过滤实时扫描，**单次写入 5.7s**（temp 目录仅 5.6ms、stat 0.15ms）。故 /readyz 稳定超时。
  ⚠️ **同类环境坑**：BFF 对 `data/` 的【真实写】也全 5.7s/次——`user_keys.json`、`admin_cred.json`、
  `request_log_*`、本地模式 multi-angle 产物落盘都受影响（多 +5.7s 延迟，不崩）。
- **修复**：`_check_state_dir` 改成 `os.path.isdir` + `os.access(DATA_DIR, os.W_OK)` 的 stat 检查
  （瞬时、不触发扫描）。`/readyz` 从 5.6s → 5ms。改完重启 BFF（新实例 v3CTKs，8300）已验证。
- **环境缓解建议（给飞哥）**：根治 data/ 写慢 → 把 `D:\code\flovart-bff\data`（或整个仓库）加入
  Windows Defender 排除项；或设 `BFF_DATA_DIR` 指向非扫描盘符；生产走 OSS（`OSS_ENABLED=1`）则不落本地。
  此坑非代码 bug，是本地防御软件对开发目录的实时扫描。

### 后续：管理员 PAT 失效根因 + 本地调试结论（飞哥问「为什么 pat 失效 / 怎么做」）
- **根因（.env 第 19–24 行已自注释）**：new-api 的 `GET /api/user/token` **每次调用都会重新生成 PAT 并作废旧值**。
  `.env` 的 `NEWAPI_ADMIN_PAT` 是一份一次性快照；只要管理员在 new-api 官方控制台点过一次
  「系统访问令牌」/token 类操作，旧 PAT 立即作废。改管理员密码、网关数据重置也会使其失效。这是**预期行为，非 bug**。
- **实测验证自愈**：用项目 venv 跑 `na.admin_request("GET","/api/user/?p=1&page_size=1")` →
  先 stale PAT 401（日志 `admin PAT rejected, re-login to rotate`）→ 自动 `_admin_login` 用
  `NEWAPI_ADMIN_USERNAME`/`PASSWORD` 重签 → `ADMIN_SELFHEAL_OK total_users=77`，admin uid=1。
  证明账密通道有效，BFF 对 register/points/管理台会自动恢复，**无需人工刷新 PAT、也无需新建管理员**。
- **本地调试结论（飞哥「先本地调试通」）**：
  1. 多角度/登录/聊天：**根本不需要管理员凭证**，已跑在 8300（Ks0jC4，WaveSpeed key 已加载），刷新前端即可测。
  2. register/积分/管理台：走账密自愈，当前 `.env` 账密有效 → 实际可用；若哪天连账密也报错，只需把
     `NEWAPI_ADMIN_PASSWORD` 改成当前管理员真实密码（同一账号，不是新建管理员）。
  3. 不要去维护 `NEWAPI_ADMIN_PAT`：它永远会被下次控制台操作作废旧值；留着只是冷启动省一次登录往返，
     401 时自动被账密覆盖。
