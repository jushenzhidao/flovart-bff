## 蓝绿切换方案设计：新端口起容器 → 验证 → 前端改指（10:16）

飞哥提议：「新起一个容器 bff，包括新的端口啥的，然后成功了再把前端指向这里」。
方向对，但有一个必须先拆的雷。

### 🔴 雷：两个 BFF 并存会互踢 PAT（代码级确认）
`app/newapi_client.py:141 _admin_login()` 内部：
1. `POST /api/user/login` 拿 access_token
2. `GET /api/user/token` ← **重新生成 PAT，作废旧值**
3. `_release_session()` 归还 session

∴ 旧进程（宝塔 8300）与新容器（8310）**共用同一个 `NEWAPI_ADMIN_UID`** 时：
任一边触发 `_admin_login()` → 作废对方 PAT → 对方 401 → 对方也重登 → **循环互踢**。
后果：日志刷 `admin PAT rejected, re-login to rotate`；高频登录逼近 new-api **50 会话上限
→ 409 → BFF 返 503**。
**但**：只要 `.env` 里 `NEWAPI_ADMIN_PAT` **有效**，两边启动时 `_load_admin_cred()` 都直接
用它、都**不走登录** → 相安无事。⇒ 触发条件不是「并存」，而是「PAT 失效」。

⚠️ 附带发现（`_save_admin_cred()` 早退）：`config.NEWAPI_ADMIN_PAT` 非空时**不落盘**，
即重登得到的新 PAT 不会写进 `admin_cred.json`。若 .env 里那个 PAT 已失效，**每次冷启
都会重新登录**（每次都会作废别人）。⇒ 「配一个失效的 PAT」比「留空」更危险。

### ✅ 安全流程（推荐）：先停宝塔 → 再起容器
测试环境，几分钟无服务无所谓，但**彻底消除互踢**。

### 有用的两点确认
1. **`/readyz` 不碰 new-api** —— 三项检查全本地（`secret_key_configured` /
   `admin_cred_configured`（只查配置有无、不登录）/ `state_dir_writable`）。
   ⇒ 起容器后先用 readyz 验证**绝不会触发互踢**。
2. **老用户能用原账号登录新容器** —— BFF 不存密码（「口令只换 PAT」），账号体系在
   new-api（同一个）⇒ 老账号照常登录。**但 SQLite 是新的**，「我的创作」/素材历史为空。

### ⚠️ 数据迁移的 chown 坑（`docker cp` 不能直接用）
- `docker cp` **保留宿主机 uid/gid**；宝塔以 root 跑 → 拷进容器后 owner 是 `0:0`
- 容器 `/data` 需要 `10001:10001`（Dockerfile 里 bff 用户）才能被 BFF 写入
  （SQLite 的 `-wal`、覆盖 `admin_cred.json`）→ **不改属主会写失败**
- 但容器 `cap_drop: ALL` ⇒ **`docker compose exec -u root bff chown` 也会失败**
  （没有 CAP_CHOWN）
- ✅ 正解：**独立 `docker run` 挂卷拷**（不受 compose 的 cap_drop 约束）：
  ```bash
  docker compose stop bff
  docker run --rm -v flovart-bff-data:/data -v "/path/to/data:/src:ro" \
    python:3.13-slim sh -c "cp -a /src/. /data/ && chown -R 10001:10001 /data"
  docker compose start bff
  ```
  （用 `python:3.13-slim` 而非 alpine，避免额外拉镜像）

### 一致性要点
- **`BFF_SECRET_KEY` 两边必须一致** → 会话 Cookie 才能跨切换继续有效（用户无感）；
  不一致 = 所有人被登出。
- `NEWAPI_ADMIN_UID` / `NEWAPI_ADMIN_USERNAME` / `NEWAPI_ADMIN_PASSWORD` 必须一致。

### 🔴 发现 2：那把共享 PAT 现在已经失效（不是隐患，是正在发生）

飞哥提供了 hewapi 线上 `.env` 的 PAT 值，**与 flovart 本地这份 sha256 完全相同**。
实测（2026-09-16）：

```
GET /api/channel/models_enabled   401
GET /api/user/?p=0&page_size=1    401
GET /api/user/self                401
响应体：{"code":"AUTH_UNAUTHORIZED","message":"Unauthorized, invalid access token"}
头写法矩阵全 401：Bearer+New-Api-User / 仅 Bearer / 裸 token / X-Api-Key
对照：GET /api/status（公开）200   ← 网关可达
对照：伪造 PAT 401                  ← 排除「端点不吃 PAT」
```

**推论**：hewapi 线上还能跑，是因为它 401 后走 `_admin_login()` 自动换新 PAT，
且因配了 PAT 而**不落盘**（`_save_admin_cred()` 开头 `if config.NEWAPI_ADMIN_PAT: return`）
→ 只存内存 → **hewapi 现在跑在一把运行时自愈出来的 PAT 上**，每次重启都会重登轮换。

**因此一条硬规则**：**绝不能照抄这串 PAT 去部署**。配了失效 PAT 后首个管理员请求就会
login → 当场踢死 hewapi 当前那把；且新 PAT 只存内存 → **每次容器重启再踢一次**。
配失效 PAT 比留空更危险（留空至少会先读 `/data/admin_cred.json` 缓存）。

**影响面（已核实，比想象中窄）**：主路径 `/api/models` 先走**用户自己的 PAT**
（`keys.py:69 _ensure_token_plain` → `_ensure_token_user`），管理员 PAT 只是 401 降级兜底
（`admin_ensure_user_api_key`）。所以互踢主要打在**管理台**（`/api/console/*`，
其中 `console.py` 三处直接调 `admin_enabled_models()`）与**冷启/降级路径**上，
不是每个普通用户请求。

**排查 hewapi 是否已在循环**：`docker compose logs bff | grep -c "admin PAT rejected, re-login to rotate"`
非 0 即说明轮换在进行。

**正解**：给 flovart 单开 new-api 管理员账号（root 登录面板 → 新建用户 → 角色管理员），
`.env` 换新账号的 UID/账密，`NEWAPI_ADMIN_PAT` 留空（首次启动登录一次自动签发并落盘
`/data/admin_cred.json`）。换账号**不影响已有用户数据**（用户各自独立，管理员账号只是
BFF 建号/加额度的操作通道）。
