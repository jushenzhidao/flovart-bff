## ⭐ 定位「新注册用户看不到平台 AI 服务」（前端 `apiKeysLoaded` 静默卡死）

飞哥反馈：新注册用户设置里「AI 服务」列表为空、PromptBar 显示「没有可用的图片 AI 服务」，
但**隔离已生效**（看不到管理员的工作流）。加日志后复现仍**「没有任何打印信息」**。

### 三线排除（后端 100% 健康，实测证据）
- `POST /api/user/login` → 双 Set-Cookie：`bff_session`(HttpOnly) + `bff_uid=118`(可读镜像) ✅
- `POST /api/me/ensure-key` → `{success:true, data:{id:128, key:"JPoXrXP4…", api_base_url:"https://workbuddy.oneapis.cn/v1"}}` ✅
- `GET /api/models` → **52 个模型**，含 2 个 seedream 图片模型（`doubao-seedream-5-0-pro-260628` 等）
  + 8 个 seedance 视频模型 ✅ → 注入 payload 的 `imageModel`/`videoModel` 必非空，`capabilities` 不会空集。
- 注：`/api/models` 是 `GET`、`/api/me/ensure-key` 是 `POST`（keys.py:102/114）；用错方法会拿到 405。

### 根因（前端）：`apiKeysLoaded` 可能永久为 false，注入 effect 被守卫静默拦截
`App.tsx` 注入 effect 的守卫 `if (!apiKeysLoaded || !hostedAuthed) { …; return; }` 是**唯一静默出口**：
一旦 `apiKeysLoaded` 永不置位，注入逻辑完全不执行，且**一条日志都不打** —— 与「没有任何打印信息」吻合。

`apiKeysLoaded` 由 `hooks/useApiKeys.ts` 的加载链置位：
`migrateLegacyKeys() → loadKeysDecrypted() → setApiKeysLoaded(true)`。
**原实现该链无 try/catch**，任一步 reject 即 unhandled rejection，置位永不执行。
高危触发场景：**注册成功→`refresh()` 检测 uid 不一致→`window.location.reload()`**，
IndexedDB 正处于上一页面连接关闭的窗口期，`vaultStorage.getItem()` reject。
（`StrictMode` 双调用本身不是问题：首次 `cancelled=true` 的早退由第二次挂载重跑覆盖。）

### 修复（前端）
- `hooks/useApiKeys.ts`：加载链包 try/catch；**无论成败最终都 `setApiKeysLoaded(true)`**（失败按空列表兜底，等价新用户无 Key）。
- `utils/keyVault.ts`：`migrateLegacyKeys()` 整体包 try/catch，绝不向外抛（localStorage 在隐私模式下访问即抛）。
- `App.tsx`：守卫日志由 `info` 升为 `warn`；新增「刷新已有平台 Key」日志（原先 update 分支静默，易误判没生效）。
- `tests/storageNamespaceIsolation.test.ts`：14 → **17 例**，新增 `apiKeysLoaded 加载链的健壮性契约`
  describe（源码级断言：链有 try/catch、catch 内无 return、置位在 catch 外、migrate 不抛）。
- 验证：17/17 绿；`tsc` 仍 16 个历史遗留、**零新增**（报错文件均为 aiGateway/dsh-plugin 等与本次无关）。

### 教训
「注入无日志」不一定是 effect 没跑，更可能是**守卫前置条件永远不满足**。
凡是「门控后续关键逻辑的 boolean 状态」，其置位路径必须有 catch 且必须保证置位，
否则故障表现为完全静默，排查成本极高。

## ⭐⭐⭐ 「平台模型不能用」终极根因 = 网关侧渠道分组配置（非代码问题）

飞哥反馈：平台模型卡出现了，但「只有一个平台模型，而且不能用」。

### 一、「只有一个模型」是【预期行为，不是 bug】
`PromptBar.tsx:936-958`：图片模式下**只按「AI 服务（key）」维度列**，每个服务只显示一个代表性图片模型
（`imageGenModel` 优先，否则从 customModels 挑第一个能映射产品目录的）。
平台服务固定显示「平台模型」+ 副标题是产品名（如 `Seedream Pro`）。
→ 所以只列出「平台模型」一条是**正确设计**：它代表「一个服务」而非「一堆模型」。
用户要换模型走 PromptBar 顶部的模型芯片，不在这里。

### 二、「不能用」的真根因（实测证据链）
1. 前端提交 → BFF `POST /api/tasks` `{type:"image-gen"}` → 默认 `mode=async` → 透传网关
   `contents/generations/tasks` → **返回 HTML 而非 JSON** → BFF 报 502：
   「网关未实现该图片端点（contents/generations/tasks 返回了前端页面而非 JSON）」
   - 渠道 `id=1 name='Tasks占位渠道可禁用'`（status=2 已禁用）就是这个异步端点的占位，**未实现**
2. 转测**同步**端点 `/v1/images/generations`（curl 直打网关）：
   `model_not_found: No available channel for model doubao-seedream-5-0-pro-260628 under group default`
   → 同步端点是**通的**（返回合法 JSON），但**模型没绑到 default 分组**
3. 用管理员凭证 `GET /api/channel/` 查渠道分组（**PAT 已失效，走账密通道 login 拿新 token**）：
   | 分组 | 启用渠道 | 图片模型 |

   | `default`（普通用户所在） | 9 个（日日新/routin/商汤/seedance/kling/bifrost…） | **❌ 0 个** |
   | `keypool` | volc 等 | ✅ `doubao-seedream-5-0-pro-260628` / `-260128`（渠道 id=21 volc） |
4. 决定性对照：同一 sk- 调 `/v1/models`（按分组过滤）→ **31 个模型，图片类 0 个**；
   而 BFF `/api/models` 返回 **52 个**（含 seedream）→ 因为 BFF 用 `na.admin_enabled_models()`

## ⭐⭐ 最终定论：「平台 AI 服务」与「用户工作流」是两个独立存储域（勿再混为一谈）

飞哥原话：「你改了好几版，要不就是可以看见管理员的工作流，要不就是看不到管理员配置的服务，
这两个是你钥匙搞混淆了吗」——**判断完全正确**。反复出问题的根源是把两件事当成一件事改。

| | 域 A：平台 AI 服务 | 域 B：用户工作流/素材 |
|---|---|---|
| 来源 | 管理员在 new-api 配的模型/渠道 | 浏览器 IndexedDB |
| 接口 | `/api/models` + `/api/me/ensure-key` | `/api/me/docs/{scope}` |
| 隔离 | **共享，所有人可用，不隔离** | **按 uid 后缀隔离，每人一份** |
| 前端 key | keyVault 里一条 `extraConfig.flovart_platform='1'` 的 Key（每人各存一份副本） | `ns()` 加 `__u<uid>` 后缀 |

**关键澄清**：平台 Key 存在每个用户**自己的** keyVault 里，这是**正确设计**（每人都该有一份自己的平台 Key 副本，
计费落各自配额）；它与工作流隔离**毫无关系**。修 A 不可能也不应该影响 B。

## ⭐ 多账号隔离真根因：hash-only 跳转不 reload（已修）

飞哥实测：「同一台机器切换普通账号登录，这工作流是刚刚我用管理员账号去做的，不应该会出现在别的账号里啊」

**根因**：多账号隔离机制的正确性依赖「登录/登出后整页 reload 重建 localforage 实例」
（`utils/storageNamespace.ts` 的 `ns()` 在**模块顶层**给实例名加 `__u<uid>` 后缀，14 个存储模块全是这个模式）。
但 `HostedGate.doHardRedirect()` 与 `useHostedStore.logout()` 原来都用
`window.location.assign(\`${pathname}#${redirectTo}\`)` —— HashRouter 下登录页 `/#/login` 到目标 `/#/`
**只有 hash 不同**，浏览器只做 hash 跳转、**不 reload 文档** → 模块顶层实例不重建
→ 新账号复用上一个账号的 localforage 实例 → 工作流/素材互串。

**修复**：
1. `components/hosted/HostedGate.tsx` `doHardRedirect` → `window.location.hash = redirectTo; window.location.reload();`
2. `stores/useHostedStore.ts` `logout()` → `window.location.hash = '/login'; window.location.reload();`
3. 加固 reload 防循环标记（`refresh()` 里 `before !== after` 的兜底 reload）：
   原实现用 `sessionStorage.getItem` 判存在 + 分支内 removeItem，**标记可能残留**导致后续真 uid 变化漏重建。
   改为 `utils/storageNamespace.ts` 导出 `clearStorageReloadMarker()` / `consumeStorageReloadMarker()`（读后即焚）/ `markStorageReload()`；
   `refresh()` 用 consume（无论有无都清），`doHardRedirect()` / `logout()` 主动 clear。

**经验（重要）**：HashRouter 应用里凡依赖「整页 reload 重建模块顶层单例」的逻辑，
**绝不能用 `location.assign()` / `location.href = '#/x'` 这类只改 hash 的方式**，必须显式 `location.reload()`。

## 隔离加固：防「跨账号误删」（飞哥提出最坏情况）

飞哥担忧：账号1 若能看到账号2 的工作流，账号1 删除它 → 账号2 的数据被删掉。

### 后端：结构上不可能（已用最强对抗测试证明）
`cloud_docs` 主键是 **`PRIMARY KEY (uid, scope, doc_key)`**（`app/db.py:28`），
即「每个账号各自持有同名 doc 的一行」。对抗测试（两个账号用**完全相同**的 doc_key

- 账号1 看到「账号1的工作流」、账号2 看到「账号2的工作流」→ 同名互不干扰 ✅
- 账号1 DELETE 自己的那条 → HTTP 200 deleted:true（删的是自己那行）
- **账号2 数据完好无损**，title 仍为「账号2的工作流」、列表齐全 ✅
- 账号1 自己的那条确实没了 ✅
→ **跨账号删除在数据库层就不成立**，无需额外防护。

⚠️ 读响应时的认知陷阱：A 对「B 的 doc_key」发 DELETE/PUT/GET 会返回 200 而非 404，
因为 A 的请求本就落在 A 自己的命名空间、成功操作了【A 自己的同名 doc】。
**看到 200 不代表越权成功** —— 必须用「B 端数据是否变化」来判定，不能只看状态码。
（同理 `_uid(session)` 让路径里的 doc_key 只是「A 空间内的键名」，不是全局资源 id。）

### 前端：加一道「归属戳」防御（纵深防御，非必需但便宜）
`services/cloudSync.ts` 模块级单例（`cloudIds`/`cloudUpdatedAt`/`dirtyIds`）在
**同一页面会话内切号**时理论上可能残留上一个账号的 id 集合。虽已由整页 reload 兜住，

- 新增 `currentUid()`（读 `useHostedStore.user.id`）+ `cloudIdsOwnerUid`（记录
  cloudIds 是哪个账号 pull 回来的，在 `pullOnce` 里写入、登出时清 null）。
- `cloudDelete()`：`cloudIdsOwnerUid !== currentUid()` 时**直接跳过不发请求**
  （宁可漏删，不可错删 —— 漏删有 pull 兜底，错删不可逆）。
- `flushPush()` 的整批删除分支同样先做归属校验。
- `flushWorkflowCloudDeletions()` 复用同一个 `cloudDelete`，自动继承校验。

问题不在删除逻辑，而在**冷启动的命名空间竞态**，且此前那版「预热」修复**根本没能生效**：

1. 所有存储模块在**模块顶层**调 `ns(base)` 建 localforage 实例（`workflow/storage.ts` 等）。
2. ES module 的 `import` 是**按源码顺序、在 import 阶段**求值的 —— 不是等到 React 渲染。
3. `index.tsx` 里 `import { RouterHost }`（第 4 行）会**传递地**把
   `components/workflow/store` → `workflow/storage` 全链条求值掉，
   而 `primeStorageNamespace()` 那句调用写在其后（原第 15 行）——**晚了**。
4. 于是首屏实例仍固定在无后缀库上；`/user/self` 回来后 `refresh()` 才写 uid 并 reload 纠正，
   但「错误的那一遍」已经读过本地数据，云同步把这份串来的数据推回云端 →
   表现为「删掉的工作流又回来 / 仍能看到别人的工作流」。

### 修复
- `utils/storageNamespace.ts`：文件**末尾加裸调用** `primeStorageNamespace();`
  —— 模块被 import 时即预热（同步读 Cookie 回填 localStorage），不再依赖调用方记得手动调。
- `index.tsx`：改成**副作用 import**，且必须放在**所有业务 import 之前**：
  ```js
  import './utils/storageNamespace';   // 必须第一行
  import React from 'react';
  import { RouterHost } from './RouterHost';
  ```
  顺序一旦调换，预热就晚于存储模块求值，隔离失效。

### BFF 侧（上一轮已完成，本轮重启验证通过）
- `app/config.py`：`UID_COOKIE_NAME = "bff_uid"`
- `app/security.py`：`set_session` 追加 `httponly=False` 的 uid 镜像 Cookie；
  `clear_session` 同属性删除。
- **实测通过**（重启 BFF 后）：登录响应同时下发
  `bff_session=...; HttpOnly` + `bff_uid=113`；登出响应两者均 `Max-Age=0` 清除。
- 为什么需要可读 Cookie：`bff_session` 是 httponly，JS 读不到；没有镜像就必须等
  `/user/self`，而那时实例早已建好。Cookie 在文档加载时就带上，填补窗口。

### 回归测试（tests/storageNamespaceIsolation.test.ts，14 例全绿）

**「模块顶层实例」+「import 静态提升」= 任何依赖运行时状态初始化存储的方案都必然晚一步。**
唯一可行解是让 uid 在 **import 阶段就能同步取到**（Cookie），并把预热做成 import 副作用、

## 【核心交付】平台共享 AI 服务：管理员配置 → 服务端存储 → 全员拉取（2026-09-11 拍板选 B）

### 飞哥诉求原文

### 根因（本会话最关键的认知）
管理员在设置页配的 AI 服务（如 `api.chatfire.cn/v1` + `gpt-image-2`）只存在
**该管理员浏览器**的 keyVault（IndexedDB）里。平台侧只有「平台 Key 池」
（`/api/me/ensure-key` → 走 new-api 渠道），**没有「服务条目」这一层** ——
于是管理员配的自定义端点永远无法共享给其他账号。之前几版改动都在
「平台 Key 池」和「工作流隔离」之间来回，从未触及这个缺口。

### 设计：两个标记，两条链路（**最容易踩的坑，务必分清**）
| | 平台 Key 池 | 平台共享服务（本次新增） |
|---|---|---|
| 标记 | `extraConfig.flovart_platform='1'` | `extraConfig.platformSource='1'` |
| 来源 | BFF `/api/me/ensure-key` 按需签发 | BFF `/api/platform/services` 管理员发布 |
| 密钥 | 每用户一把自己的 new-api token | **管理员那把 key 下发给所有人** |
| 链路 | BFF 网关代发 → new-api 计费落各自配额 | 用户侧持 key **直连**管理员配的端点 |
| 计费 | new-api | 不经过 new-api（平台承担成本） |
二者**并存不互斥**，不得复用同一标记 —— 若共享服务带上 `flovart_platform`，
前端 `aiGateway.isHostedPlatform()` 会误判为网关代发 → 不用这把 key、绕开计费。

## 平台共享服务：图片链路两处修复（普通用户「API Key 无效」+ 图生图 422）

飞哥反馈：「普通用户可以看到了，但是使用时报错 API Key 不对，浏览器里接口请求带的是

### Bug 1 —— 普通用户图片生成用本地假 key 直连上游（401）

**根因（不对称）**：`aiGateway.isHostedPlatform()` **只认** `flovart_platform === '1'`
（平台 Key 池标记），而平台共享服务注入的是 `platformSource === '1'` → 判为非平台模式
→ 掉进 BYOK 直连分支 → 读 keyVault 里该条目的 key。用户本地残留一条同 routeId 的

**修复**：把判定拆成两个谓词并取并集，同时**图片路径补上视频路径早就有的 `_gateway` 注入**：
```ts
function isHostedPlatform(key?) {
  if (useHostedStore.getState().status !== 'authed') return false;
  return isPlatformKeyPool(key) || isPlatformSharedService(key);
}
function platformSharedGatewayParams(key) {  // 共享服务才带；Key 池不带
  if (!isPlatformSharedService(key)) return null;
  const baseUrl = key?.baseUrl?.trim(), apiKey = key?.key?.trim();
  return baseUrl && apiKey ? { base_url: baseUrl, api_key: apiKey } : null;
}
```
注入点两处：`generateImageWithProvider`（image-gen）与 `runImageAgentWithProvider`（图片工具）。

> **平台 Key 池**绝不能带（BFF 用管理员凭证代发走 new-api，计费落各自配额）。

## 【根因定位 + 修复】管理员图生图 `Network Error` = nginx 60s 掐断（非上游 500）

飞哥截图：左图画布节点红条 `任务未返回媒体`，右图 DevTools 瀑布流全是重复 `tasks` 请求。

1. `hostedClient.api()` 只在 **fetch 本身 reject** 时才抛原生错误；BFF 返回 500/504
   会被转成 `请求失败(N)` 中文文案。→ 出现裸 `Network Error` ⇒ **请求根本没拿到响应**。

- **裸 `Network Error` / `Failed to fetch` ⇒ 连接层断，绝不是 HTTP 状态码问题。**
  有响应体就一定走 `!res.ok` 分支给出 `请求失败(N)`。排查时先分清这两类。
- **同步阻塞代理 + 反代默认超时 = 定时炸弹**。凡是「BFF await 上游几十秒」的端点，
  要么改异步提交+轮询，要么把反代超时提到明显大于上游 P99。
- 即使进程内 `create_task` 在单 worker 下够用，**跨重启会丢在途任务**（日志停在 processing），
  前端轮询超时重试即可，不会产生脏数据 —— 已在注释中写明取舍。
