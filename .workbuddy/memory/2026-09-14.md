## 【修复】平台服务重复条目 + 管理员可编辑/删除（飞哥截图反馈）

飞哥截图：设置页「平台服务」区并列**两条一模一样**的 `OpenAI / https://api.chatfire.cn/v1`，
都是「只读」，问「想删除掉一个，发现没有编辑的地方」。

### 根因（两个问题叠加）

**问题 1：重复条目的来源 —— 去重键用了本机随机 id**
`SettingsPanel.handlePublishToPlatform` 原第 698 行按 `s.id !== entry.id` 去重，
而 `entry.id = itemKey.id` 是**本机 keyVault 的随机 id**。同一条服务在
导出/导入、清库重建后 id 会变；管理员先后用「本地两条不同 id 但内容相同」的条目发布，
服务端（`cloud_docs` uid=0/scope=platform/doc_key=services，**整体覆盖**语义）
就累积出两条相同服务。
→ 新增 `sameService(a, b)` 按**服务身份**（provider + baseUrl(去尾斜杠) + imageGenModel +
videoGenModel + defaultModel）判定同一条；发布时 `existing = 按 id 找 || 按身份找`，
沿用服务端已有条目的 id（而非本机 id）；`others` 过滤同时排除同 id 与同身份
（**顺带清掉历史遗留的重复项**）。

**问题 2：管理员无处可改 —— 平台服务区对所有人一视同仁只读**
原设计注释写「要改请让管理员去自己的设置页改后重新发布」，但实际上：
- 本机那几条（`managedApiKeys`）与服务端条目**未必一一对应**（本地可能已删、id 可能变过）
- 影子条目是服务端下发的，走 `onUpdateApiKey` 只会改本机、下轮拉取即被覆盖

→ 给**管理员**在「平台服务」区加内联编辑表单 + 删除按钮（普通用户保持只读）：
- `editingPlatformId` / `platformDraft` / `savingPlatform`（**与 BYOK 的 `editingKeyId` 分开管理**）
- `beginEditPlatform` / `cancelEditPlatform` / `savePlatformDraft`（整体覆盖服务端列表）
- `removePlatformServiceById(serviceId)`（按服务端 id 删，供编辑区与删除按钮复用）
- 表单字段：名称 / Base URL / API Key / 生图模型 / 视频模型 / 支持能力（text·image·video 复选）
- 删除/保存后调 `useHostedStore.getState().loadPlatformServices()` 立即刷新影子条目

### 踩坑
- 我一度引入 `var(--isl-accent)` —— **项目里没有这个变量**。实际用的是
  `--isl-mint`（主按钮底色）/ `--isl-mint-deep`（链接色）。已改正。
- 源码级测试断言里 `readFileSync(new URL(...))` 会被本机 fs broker shim 拦（`TypeError: The URL must be of scheme file`），
  **改用相对字符串路径** `readFileSync('components/SettingsPanel.tsx', 'utf8')` 即可。

### 验证
- `tests/platformSharedService.test.tsx` **11 passed**（新增 4 例：管理员有编辑/删除 /
  普通用户仍只读 / 点编辑展开表单 / 去重键按服务身份）
- 相关套件 **51 passed**（+ routing 3 + gateway 10 + storageNamespaceIsolation 27）
- `tsc --noEmit` 对 SettingsPanel **零新增**

### 经验
**「服务端下发 + 本机影子条目」的双层结构，一定要给数据真身所在的层留管理入口。**
只读展示对普通用户是对的，但对管理员必须有编辑/删除 —— 否则一个小改动就得去服务器改 SQLite。
另外：**跨设备/跨会话的资源去重，绝不能用本机随机 id 作键**，必须用「业务身份」。

## 【分支策略反转】平台服务语义改造从 main 移到 dev（飞哥中途纠偏）

### 背景
飞哥先提出需求 E：「管理员在设置页配网关模型 → 用户选模型、用自己默认 Key 调用；
也可以自己配网关/模型/Key（= 原有 BYOK，不动）」。我据此刻画并落地为
**「平台服务 = 模型清单（不含密钥）」新语义**，并把「共享 Key」旧语义**整体替换**。

随后飞哥打断纠偏：**「目前版本还是以公共平台服务为主，我需要拉一个新的分支来开发
后续接入网关模型的需求，也就是我新拉的 dev 分支，main 分支还是回退到之前的代码」**。

### ⚠️ 两种平台服务语义（务必分清，勿再混用）
| | **旧语义（main 保留）** | **新语义（dev 开发）** |
|---|---|---|
| 平台服务内容 | 完整服务条目：`key` + `baseUrl` + 模型 | **仅模型清单**（无 key/baseUrl） |
| 用户怎么调 | 持**管理员 key** 直连管理员配的端点 | 用**自己的默认 Key**（`/api/me/ensure-key` 签发的 sk-）+ BFF 下发的 `gatewayBaseUrl` |
| 是否经 new-api 计费 | ❌ 不经（平台自担成本） | ✅ 经，落**用户自己的配额** |
| `_gateway` | **必须带**（BFF `_run_external` 直连） | **绝不能带**（带了绕开计费） |
| `_ALLOWED_FIELDS` | 含 `key`/`baseUrl` | 移出，且加 `_FORBIDDEN_FIELDS = ("key","baseUrl")` |
| 去重键 | `provider + baseUrl + 模型` | `provider + name + models` |
| 标记 | `extraConfig.platformSource='1'` | 同左（标记不变，语义变） |

（`flovart_platform='1'` 是**平台 Key 池**标记，与 `platformSource` 是两条链路，均不可混用；
`_sanitize` 强制剔除 `flovart_platform` 与 `_gateway`。）

### 执行结果
- **dev 分支**：保留新语义全套改造（BFF `platform_services.py` + 前端 5 文件 + 新测试）
- **main 分支**：手工反向改回旧语义，提交 `f08ff71`(web) / `8acc81d`(bff)
  - 回退点：BFF `_ALLOWED_FIELDS` 恢复 `key`/`baseUrl`、`_redact` 恢复 `keyPresent`、
    GET 去掉 `gatewayBaseUrl`（并去掉 `config` import）、移除 `_FORBIDDEN_FIELDS`；
    前端 `hostedClient`/`useHostedStore`/`aiGateway`/`App.tsx`/`SettingsPanel` 共 5 文件；
    删除 dev 专属 `tests/platformServiceModelList.test.ts`；`platformSharedService.test.tsx` 回旧语义
  - 验证：`test_smoke.py` **13 passed**；前端相关套件 **47 passed**；回退的 5 个文件 `tsc` **零错误**

### ⚠️ 踩坑（重要）
1. **本仓库没有真正的「改造前」提交** —— `5ad25eb`(web) / `6538bc7`(bff) 这个 init commit
   **已经包含**新语义改造。tag `dev-baseline-20260914` 也指向该 commit（= 新语义），
   **不是改造前快照**。故 main 回退只能**手工反向改写**，不能用 `git checkout <ref>`。
   → 教训：**动手改造前应先打一个真·基线 tag**，否则回退成本高且易漏。
2. **测试失败要先做对照组**：`tests/test_external_gateway_errors.py` 有 2 条失败
   （`DID NOT RAISE`，与 `_run_external` 异常吞没有关）。用 `git checkout HEAD~1` 跑同样失败，
   证明是**既存问题**、与本次回退无关。**不要顺手去"修"不在范围内的失败测试。**
3. BFF 测试必须用专属 venv：`C:\Users\81068\.workbuddy\binaries\python\envs\flovart-bff\Scripts\python.exe`
   （默认 `envs\default` 没装 pytest），且必须 `cd` 到仓库后用**相对路径**（`/d/...` 路径会报 file not found）。

### 经验
**语义级改造如果可能"推倒重来"，先拉分支再动手。** 这次是改造完才发现方向要分叉，
被迫在两个仓库手工反向回退 7 个文件 —— 若当初先在分支上做、main 保持不动，成本几乎为零。
