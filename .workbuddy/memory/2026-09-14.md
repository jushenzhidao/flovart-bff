## 【修复】平台服务重复条目 + 管理员可编辑/删除（飞哥截图反馈）

飞哥截图：设置页「平台服务」区并列**两条一模一样**的 `OpenAI / https://api.chatfire.cn/v1`，
都是「只读」，问「想删除掉一个，发现没有编辑的地方」。

### 根因（两个问题叠加）

**问题 1：重复条目的来源 —— 去重键用了本机随机 id**
`SettingsPanel.handlePublishToPlatform` 原第 698 行按 `s.id !== entry.id` 去重，
而 `entry.id = itemKey.id` 是**本机 keyVault 的随机 id**。同一条服务在
导出/导入、清库重建后 id 会变；管理员先后用「本地两条不同 id 但内容相同」的条目发布，
服务端（`cloud_docs` uid=0/scope=platform/doc_key=services，**整体覆盖**语义）
就累积出两条相同服务。
→ 新增 `sameService(a, b)` 按**服务身份**（provider + baseUrl(去尾斜杠) + imageGenModel +
videoGenModel + defaultModel）判定同一条；发布时 `existing = 按 id 找 || 按身份找`，
沿用服务端已有条目的 id（而非本机 id）；`others` 过滤同时排除同 id 与同身份
（**顺带清掉历史遗留的重复项**）。

**问题 2：管理员无处可改 —— 平台服务区对所有人一视同仁只读**
原设计注释写「要改请让管理员去自己的设置页改后重新发布」，但实际上：
- 本机那几条（`managedApiKeys`）与服务端条目**未必一一对应**（本地可能已删、id 可能变过）
- 影子条目是服务端下发的，走 `onUpdateApiKey` 只会改本机、下轮拉取即被覆盖

→ 给**管理员**在「平台服务」区加内联编辑表单 + 删除按钮（普通用户保持只读）：
- `editingPlatformId` / `platformDraft` / `savingPlatform`（**与 BYOK 的 `editingKeyId` 分开管理**）
- `beginEditPlatform` / `cancelEditPlatform` / `savePlatformDraft`（整体覆盖服务端列表）
- `removePlatformServiceById(serviceId)`（按服务端 id 删，供编辑区与删除按钮复用）
- 表单字段：名称 / Base URL / API Key / 生图模型 / 视频模型 / 支持能力（text·image·video 复选）
- 删除/保存后调 `useHostedStore.getState().loadPlatformServices()` 立即刷新影子条目

### 踩坑
- 我一度引入 `var(--isl-accent)` —— **项目里没有这个变量**。实际用的是
  `--isl-mint`（主按钮底色）/ `--isl-mint-deep`（链接色）。已改正。
- 源码级测试断言里 `readFileSync(new URL(...))` 会被本机 fs broker shim 拦（`TypeError: The URL must be of scheme file`），
  **改用相对字符串路径** `readFileSync('components/SettingsPanel.tsx', 'utf8')` 即可。

### 验证
- `tests/platformSharedService.test.tsx` **11 passed**（新增 4 例：管理员有编辑/删除 /
  普通用户仍只读 / 点编辑展开表单 / 去重键按服务身份）
- 相关套件 **51 passed**（+ routing 3 + gateway 10 + storageNamespaceIsolation 27）
- `tsc --noEmit` 对 SettingsPanel **零新增**

### 经验
**「服务端下发 + 本机影子条目」的双层结构，一定要给数据真身所在的层留管理入口。**
只读展示对普通用户是对的，但对管理员必须有编辑/删除 —— 否则一个小改动就得去服务器改 SQLite。
另外：**跨设备/跨会话的资源去重，绝不能用本机随机 id 作键**，必须用「业务身份」。

## 【设计】持久化分层：草稿自动 + 正式手动（飞哥拍板，待开发）

### 起因
飞哥问「怎么做本地优先 + 云端持久化 + 换设备看历史？是不是手动保存才上云」。
**纠正了他一个前提**：现状**已经是全自动双向同步**（`cloudSync.ts`：登录 pullOnce 合并 +
改动 800ms 防抖 push），**不是手动才上云**。他要的能力其实基本已具备。

### 现状（准确地图，勿再误判）
| 能力 | 现状 | 位置 |
|---|---|---|
| 本地主存 | IndexedDB（zustand persist，按 uid ns 隔离） | `workflow/store.ts` |
| 工作流云同步 | **全自动**：pullOnce 合并 + 800ms 防抖 push | `services/cloudSync.ts` |
| 生成历史 | 整体覆盖 `scope=history/doc_key=generations`，最近 **18** 条 | `services/historyCloudSync.ts` |
| 素材字节 | `cloud_media`，快照存 `cloudMediaKey` | `cloudSync.ts`→`media.ts` |
| BFF | `cloud_docs`(5MB/doc) + `cloud_media`(50MB) + `base_revision` 乐观锁 | `app/cloudstore.py`/`routers/cloud.py` |
| **删除** | **硬删除**，多端消失，**无回收站** | `cloudSync.ts:83` |

**真实痛点**：① 无草稿/正式之分（空项目也同步，列表堆垃圾）② 写放大（每次改动整份 PUT）
③ 删除不可逆。

### 拍板结论（飞哥 2026-09-14）
- **方案 B：草稿自动 + 正式手动**
- 草稿频率：**维持 800ms 不改**
- 正式版删除：**软删除进回收站**
- 生成历史：**18 条够用，不改**

### 方案要点（详见 `DESIGN-draft-vs-saved.md`）
- **草稿层**：完全沿用现状（`scope=projects`，doc_key=项目 id），零改动。
- **正式层**：**独立 doc_key = `<项目id>@v<N>`**（不是同 doc 塞版本数组 —— 5MB 上限会被撑爆，
  且每次 PUT 全量重写不可持续）。payload 嵌 `snapshot` 字段。
- **软删除 v1 用「payload 内 `deletedAt` + PUT 覆盖」**，**零 BFF DDL 改动**（PG/SQLite 两套
  后端都不用迁）。列表加 `?include_deleted=1` 复用现有接口。等配额成真问题再迁 DDL。
- **正式版就是普通 doc**，不新增表/接口。
- 新增前端函数：`saveProjectVersion` / `listProjectVersions` / `restoreProjectVersion` /
  `softDeleteProjectVersion` / `restoreDeletedProjectVersion`。
- 工作量约 **2-2.5 天**（P1 纯前端 + 现有 API → P2 UI → P3 软删 → P4 跨设备回归）。

### 设计经验
**「自动同步」和「用户主动保存」解决的是两个不同问题**：前者防丢失，后者给掌控感与归档语义。
把两者混成一件事（现状），结果就是「什么都同步了，但用户觉得什么都没存」。
分层后：草稿保底不丢，正式版是用户主动的作品 —— 各司其职。
另外：**加"版本"概念时优先用独立 doc_key，别在单文档里塞数组**（对象存储的单文档大小上限是硬约束）。

## 【已落地】生成历史改「索引 doc + 缩略图走 cloud_media」，上限 18 → 200

### 起因
飞哥问「生成历史上限调整是啥意思」，解释后他拍板：**换成 cloud_media 存缩略图 + doc 只存索引**。
（原形态：缩略图 base64 内联在 `cloud_docs` 的 `items[].dataUrl`，18 条就逼近单文档 5MB，
上限是被体积倒逼卡在 18 的。）

### 实现（前端，dev 分支，提交 `413b9e3`；**BFF 零改动**）
| 文件 | 改动 |
|---|---|
| `types/index.ts` | `GenerationHistoryItem` 加可选 `thumbKey?: string` |
| `utils/generationHistory.ts` | `MAX_HISTORY_ITEMS` 18 → **200** |
| `services/historyCloudSync.ts` | **核心重写**（见下） |
| `App.tsx` | 生成即上传 + 渲染用 `resolveHistoryThumb` |
| `tests/generationHistory.test.ts` | 截断断言 18 → 200 |
| `tests/historyCloudSync.test.ts` | **新增 10 例** |

### `historyCloudSync.ts` 新契约（关键，勿破坏）
1. **doc 只存索引**：`toCloudIndex()` 把 `dataUrl` 清空，只留 `thumbKey` + 元数据 → doc 从数 MB 降到几十 KB。
   payload 加 `version: 2` 标记格式。
2. **缩略图走 `cloud_media`**：`uploadMediaToBff(blob, 'history-thumb')` → `media_key` 存进 `thumbKey`。
   读用 `resolveHistoryThumb(item)`：有 thumbKey → `/api/me/media/{key}`（BFF 307 到 OSS presigned）；否则回退 dataUrl。
3. **生成即上传**（`uploadHistoryThumb`，在 `App.saveGenerationToHistory` 里调用，不等 800ms 防抖 push）：
   push 只剩纯索引 PUT，且刷新/关页不丢待传图。失败静默，push 时兜底重试。
4. **push 前 `ensureThumbKeys` 兜底补齐**（幂等）：
   - 已有 `thumbKey` → 跳过；
   - **非 `data:` 开头的 dataUrl**（如 pull 回填的 `/api/me/media/...`）→ **也跳过**（否则会 fetch 一个 URL 再上传，白费流量）；
   - 单条失败不阻断其余，留空下次重试。
5. **`mergeHistoryItems` 保留 `thumbKey`**：同 id 条目即使较新侧没有 thumbKey，也不覆盖掉旧侧的
   —— 否则会把已上传的云端引用退化成待上传的内联 base64，导致重复上传。
6. **`pullHistoryOnce` 回填 dataUrl**：索引里 dataUrl 是空的，pull 时回填成缩略图 URL，
   让下游所有按 `item.dataUrl` 渲染的既有代码（工作流素材面板等）**无需改造**即可正确显示。
7. **老 base64 数据不迁移**（飞哥拍板）：渲染兼容两种形态，随上限淘汰自然退场。

### 验证
- 新增 `tests/historyCloudSync.test.ts` **10 passed**（覆盖：剥离正文 / 幂等跳过 / 失败不阻断 /
  merge 保留 thumbKey / pull 回填 / 404 / 上传成功与失败）
- 相关套件 **44 passed**（+ generationHistory 3 + recipePackage 4 + storageNamespaceIsolation 27）
- 改动文件 `tsc --noEmit` **零错误**（总 16 个错误全是既存的 `dsh-plugin/*` 等无关文件）

### 经验
**「小文档 + 大二进制外置」是对象存储场景的通用解法。** 单文档大小上限（这里是 5MB）一旦成为
功能约束（把历史上限倒逼到 18），就该把二进制挪到 blob 存储、doc 只留引用 ——
索引小到可以整体覆盖写，不必上增量更新。
另外：**给字段加引用形式时，务必在读取侧做「回填」**（这里是 pull 时把 thumbKey 还原成 dataUrl），
这样下游既有代码一行都不用改，改造面被收敛在同步层内部。

## 【严重事故 + 修复】flovart-web 的 git 对象库丢失 → 重建仓库

### 事故
清理 flovart-web 工作区时，git 的 `.git/refs/` 目录与 `.git/objects/pack/*.pack`
**同时消失**（只剩 `.idx` 和 `multi-pack-index`），导致 `.git` 被 git 判定为
`not a git repository`，重建 refs 后又报 `bad object HEAD`。

### 影响面（关键结论）
- **工作区文件 100% 完好** —— 所有代码改动（历史索引化 / P1 版本层 / P2 UI）都在。
- 丢失的是 **commit 对象**：`5ad25eb`(init) / `f08ff71`(main) / `413b9e3`(历史索引化) /
  `c5aa937`(P1 版本层) / `b48def8` 之前的全部提交历史。
- `origin` 远端的 reflog 显示只推过 `5ad25eb` 和 `f08ff71`；**`413b9e3` 与 `c5aa937`
  从未推送**，故不可从远端恢复。全盘 find 确认 `.pack` 文件不存在。

### 处置
1. 备份损坏仓库 → `D:/code/flovart-web-git-broken-backup`
2. 导出 reflog 到 `/tmp/flovart-web-reflog-{HEAD,dev}.txt`（保留追溯线索）
3. `rm -rf .git` → `git init -b dev` → 重加 remote origin
4. 把**全部工作区**（含本轮所有改动）作为新基线提交
5. `git fsck` 无输出 = 仓库健康

### 教训（务必牢记）
- **不要在 git 仓库里做未预期的批量文件操作**；`.git` 是工作区之外的高危区。
- **重要提交要尽早 push**。本地分支上未推送的 commit 一旦对象库损坏就永久丢失 ——
  本次 `413b9e3`/`c5aa937` 正是这种情况。
- 仓库损坏时，**优先固守工作区**（那才是真实交付物），别急着反复操作 `.git`。
