## 【修复】平台服务重复条目 + 管理员可编辑/删除（飞哥截图反馈）

飞哥截图：设置页「平台服务」区并列**两条一模一样**的 `OpenAI / https://api.chatfire.cn/v1`，
都是「只读」，问「想删除掉一个，发现没有编辑的地方」。

### 根因（两个问题叠加）

**问题 1：重复条目的来源 —— 去重键用了本机随机 id**
`SettingsPanel.handlePublishToPlatform` 原第 698 行按 `s.id !== entry.id` 去重，
而 `entry.id = itemKey.id` 是**本机 keyVault 的随机 id**。同一条服务在
导出/导入、清库重建后 id 会变；管理员先后用「本地两条不同 id 但内容相同」的条目发布，
服务端（`cloud_docs` uid=0/scope=platform/doc_key=services，**整体覆盖**语义）
就累积出两条相同服务。
→ 新增 `sameService(a, b)` 按**服务身份**（provider + baseUrl(去尾斜杠) + imageGenModel +
videoGenModel + defaultModel）判定同一条；发布时 `existing = 按 id 找 || 按身份找`，
沿用服务端已有条目的 id（而非本机 id）；`others` 过滤同时排除同 id 与同身份
（**顺带清掉历史遗留的重复项**）。

**问题 2：管理员无处可改 —— 平台服务区对所有人一视同仁只读**
原设计注释写「要改请让管理员去自己的设置页改后重新发布」，但实际上：
- 本机那几条（`managedApiKeys`）与服务端条目**未必一一对应**（本地可能已删、id 可能变过）
- 影子条目是服务端下发的，走 `onUpdateApiKey` 只会改本机、下轮拉取即被覆盖

→ 给**管理员**在「平台服务」区加内联编辑表单 + 删除按钮（普通用户保持只读）：
- `editingPlatformId` / `platformDraft` / `savingPlatform`（**与 BYOK 的 `editingKeyId` 分开管理**）
- `beginEditPlatform` / `cancelEditPlatform` / `savePlatformDraft`（整体覆盖服务端列表）
- `removePlatformServiceById(serviceId)`（按服务端 id 删，供编辑区与删除按钮复用）
- 表单字段：名称 / Base URL / API Key / 生图模型 / 视频模型 / 支持能力（text·image·video 复选）
- 删除/保存后调 `useHostedStore.getState().loadPlatformServices()` 立即刷新影子条目

### 踩坑
- 我一度引入 `var(--isl-accent)` —— **项目里没有这个变量**。实际用的是
  `--isl-mint`（主按钮底色）/ `--isl-mint-deep`（链接色）。已改正。
- 源码级测试断言里 `readFileSync(new URL(...))` 会被本机 fs broker shim 拦（`TypeError: The URL must be of scheme file`），
  **改用相对字符串路径** `readFileSync('components/SettingsPanel.tsx', 'utf8')` 即可。

### 验证
- `tests/platformSharedService.test.tsx` **11 passed**（新增 4 例：管理员有编辑/删除 /
  普通用户仍只读 / 点编辑展开表单 / 去重键按服务身份）
- 相关套件 **51 passed**（+ routing 3 + gateway 10 + storageNamespaceIsolation 27）
- `tsc --noEmit` 对 SettingsPanel **零新增**

### 经验
**「服务端下发 + 本机影子条目」的双层结构，一定要给数据真身所在的层留管理入口。**
只读展示对普通用户是对的，但对管理员必须有编辑/删除 —— 否则一个小改动就得去服务器改 SQLite。
另外：**跨设备/跨会话的资源去重，绝不能用本机随机 id 作键**，必须用「业务身份」。

## 【分支策略反转】平台服务语义改造从 main 移到 dev（飞哥中途纠偏）

### 背景
飞哥先提出需求 E：「管理员在设置页配网关模型 → 用户选模型、用自己默认 Key 调用；
也可以自己配网关/模型/Key（= 原有 BYOK，不动）」。我据此刻画并落地为
**「平台服务 = 模型清单（不含密钥）」新语义**，并把「共享 Key」旧语义**整体替换**。

随后飞哥打断纠偏：**「目前版本还是以公共平台服务为主，我需要拉一个新的分支来开发
后续接入网关模型的需求，也就是我新拉的 dev 分支，main 分支还是回退到之前的代码」**。

### ⚠️ 两种平台服务语义（务必分清，勿再混用）
| | **旧语义（main 保留）** | **新语义（dev 开发）** |
|---|---|---|
| 平台服务内容 | 完整服务条目：`key` + `baseUrl` + 模型 | **仅模型清单**（无 key/baseUrl） |
| 用户怎么调 | 持**管理员 key** 直连管理员配的端点 | 用**自己的默认 Key**（`/api/me/ensure-key` 签发的 sk-）+ BFF 下发的 `gatewayBaseUrl` |
| 是否经 new-api 计费 | ❌ 不经（平台自担成本） | ✅ 经，落**用户自己的配额** |
| `_gateway` | **必须带**（BFF `_run_external` 直连） | **绝不能带**（带了绕开计费） |
| `_ALLOWED_FIELDS` | 含 `key`/`baseUrl` | 移出，且加 `_FORBIDDEN_FIELDS = ("key","baseUrl")` |
| 去重键 | `provider + baseUrl + 模型` | `provider + name + models` |
| 标记 | `extraConfig.platformSource='1'` | 同左（标记不变，语义变） |

（`flovart_platform='1'` 是**平台 Key 池**标记，与 `platformSource` 是两条链路，均不可混用；
`_sanitize` 强制剔除 `flovart_platform` 与 `_gateway`。）

## 前端模型展示兜底（B 方案）— 2026-09-14 傍晚

### 背景（飞哥提报的 bug）
设置页显示管理员配的 2 个平台服务（`gpt-image-2` / `gpt-image-2.5`）正常，但

### 根因（两个独立 bug，同一源头）
源头：`gpt-image-2.5` **没登记进产品目录** → `getProductModel('gpt-image-2.5')` 返回 `undefined`。
- **bug①「名字都变 gpt-image-2」**：`PromptBar.tsx` 副标题用 `getProductModel(model)?.name`，
  映射失败 → 无名；而 `SettingsPanel.tsx:1545` 有 `|| item.imageGenModel` 兜底 → 能显示原名。
  **两处兜底策略不一致**。
- **bug②「2 个服务显示 3 条」**：`PromptBar.tsx` 的 model 取值 `key.imageGenModel || fallback || ''`，

### 落地方案（飞哥拍板 B：兜底友好）

## 【修复】服务卡片显示错模型 + PromptBar 多出条目（飞哥 2026-09-14 晚，gpt-image-2.5 后续）

飞哥截图三连：① 编辑弹窗「模型名称」填 `gpt-image-2.5`；② 服务卡片副标题却显示

- `SettingsPanel.tsx` 卡片副标题原为 `{item.defaultModel && <>· 默认 {item.defaultModel}</>}`
  → 读 **`defaultModel`**

const merged = [...withoutShared, ...sharedEntries];   // sharedEntries 来自服务端

## 【修复·真 bug】选中 gpt-image-2.5 提交却弹「配置 AI 服务」—— `keyExposesRoute` 漏读 imageGenModel

飞哥截图：PromptBar 已显示 `GPT Image 2.5`，点提交却弹出配置服务弹框（= 判定不可用）。

### 定位链路（PromptBar 提交 → 弹框）
`PromptBar.tsx:550` `handleEditorSubmit`
→ `L558 if (readyState === 'missing-key') { onOpenSettings?.(); return; }` ← **弹框就是这里**
→ `L497 readyState = missingImageModel || (!providerOptional && (!activeKey || (activeProductModel && !activeRoute)))`
→ `promptBarPolicy.ts:91` `activeRoute = resolveProductModelRoute(activeProductModel.id, activeSubmode, userApiKeys)`
→ `productModelCatalog.ts:497` `resolveRouteMapping({kind:'product-mode', productModelId, mode}, keys)`
→ `routeMapping.ts:66` `candidates.find(({key,mapping}) => routeAvailable(key, target, mapping.routeId))`
→ `routeMapping.ts:35` `keyExposesRoute(key, routeId)` ← **返回 false，导致 selected=undefined → 返回 null**

### 根因：两个函数的「字段口径」不一致
| 函数 | 位置 | 读取字段 |
|---|---|---|
| `keyModels()`（**生成**映射用） | `productModelCatalog.ts:446` | `defaultModel` + **`imageGenModel`** + `models[].id` + `customModels` |
| `keyExposesRoute()`（**校验**可用性用） | `routeMapping.ts:18` | `defaultModel` + ~~imageGenModel~~ + `models[].id` + `customModels` |

用户在「编辑 AI 服务」里只改「模型名称」（= 只写 `imageGenModel`，`customModels` 仍是
`gpt-image-2`）后：
- **生成映射 ✅**（`keyModels` 含 imageGenModel → 映射里确实有 `flovart:gpt-image-2.5`）
- **校验可用 ❌**（`keyExposesRoute` 读不到 → `includes('gpt-image-2.5')` = false）
- ⇒ `activeRoute = null` ⇒ `missing-key` ⇒ **点提交弹配置框**

**实测复现**（临时测试，已删）：`imageGenModel='gpt-image-2.5'` + `customModels:['gpt-image-2']`
→ `resolveRouteMapping` **NULL**；把 2.5 也塞进 `customModels` → **OK:gpt-image-2.5**。

### 修复
`services/routeMapping.ts` `keyExposesRoute` 的字段列表补上 `key.imageGenModel`，
与 `keyModels()` 对齐并加注释说明口径必须一致。

### ⚠️ 顺带发现的另外两个隐患（**未修，待飞哥决策**）
1. **`platformModelGate` 宽松匹配有子串误命中**：`selfNames` 含 `def.id`
   （如 `flovart:gpt-image-2.5`），与平台名做**双向 `includes`** 时，
   `'flovart:gpt-image-2.5'.includes('gpt-image-2')` = **true**
   → 实测 `flovart:gpt-image-2.5` 被 `gpt-image-2` **误判为可用**。
   （当前方向是"误放行"，用户侧表现为能选但调用可能失败；
   同类还有 `gpt-image-1.5` vs `gpt-image-1`。）建议改为「按 `-` 分段的前缀匹配」或

2. **`defaultModel` 与 `imageGenModel` 永不同步**：编辑弹窗只写 `imageGenModel`，
   而卡片/多处展示读 `defaultModel`（本轮已把卡片改为优先 `imageGenModel`，
   但两个字段的语义重叠仍在，长期建议收敛为单一字段）。

### ⚠️ 网关模型命名注意
`GET /api/models`（33 个）里**没有 `gpt-image-2.5`**，只有两个变体：
`gpt-image-2.5-flare`、`gpt-image-2.5-sunburst`。而产品目录登记的是

### 经验
**「生成」与「校验」两段逻辑读同一实体的字段集合必须完全一致。**
本次是 `keyModels()`（生成）含 `imageGenModel`、`keyExposesRoute()`（校验）不含 ——
写的时候都对，分头看都合理，合起来就造成「映射存在却解析不出」的诡异现象。
**排查此类问题的最快路径：先找到最终抛错/拦截的那一行，再逐层向上追参数来源。**
另外：**依赖登录态的后端清理逻辑，会在后端挂掉期间「停止工作」**，
造成本地脏数据长期残留 —— 排查本地数据不一致时要把这类守卫条件算进去。
